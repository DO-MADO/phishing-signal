# 연구에서 제품까지

[← 제품 소개](../README.md)

피싱 신호등의 개발은 규칙 기반 탐지에서 시작했습니다. 모델과 데이터 구성을 여러 차례 바꾼 이유는 “위험한 단어를 찾기”와 “실제로 위험 행동을 요구하는 연락인지 판단하기” 사이에 차이가 있었기 때문입니다.

이 문서는 개발 기록의 결정을 공개용으로 재구성한 요약입니다. 아래 단계는 시간순 설계 변화이며, 동일 평가 조건에서의 연속적인 성능 상승을 뜻하지 않습니다.

## 1. 규칙으로 시작해 문맥의 문제를 발견했습니다

인증번호, 송금, 앱 설치 등의 표현은 빠르게 찾을 수 있습니다. 하지만 위험 행동을 요구하는 문장과 그 행동을 하지 말라는 예방 안내에는 같은 단어가 등장합니다. 단어의 존재만으로 위험 여부를 결정하면 정상 안내까지 경고할 수 있습니다.

**남긴 결정:** 규칙은 명시적인 표현과 관계를 확인하는 데 활용하되, 전체 문맥 분류와 화면 참고 표현을 구분합니다.

## 2. 여러 모델과 결합 방식을 비교했습니다

경량 분류기와 한국어 사전학습 문맥 모델, 규칙·모델의 하이브리드 구성, C3 단일 구성을 검토했습니다. 초기에는 가벼운 판단 이후 필요한 경우에만 더 큰 모델을 호출하는 캐스케이드도 실험했습니다.

**남긴 결정:** 현재는 C3 문맥 모델이 기본 판정을 만들고, Safe에 한해 엄격한 규칙 근거를 확인하는 구조입니다. 과거 실험의 복잡한 라우팅을 현재 제품의 기능으로 내세우지 않습니다.

## 3. 데이터의 양보다 입력과 라벨 기준을 다시 봤습니다

연구 과정에서 사용자가 실제로 붙여넣을 연락과 설명·보고 형식의 문장을 구분해야 했습니다. 직접 요청, 인용, 거절, 예방, 완료된 행동, 판단에 필요한 정보가 빠진 문장을 같은 단어 집합으로 취급하지 않도록 데이터 기준과 검수 과정을 재검토했습니다. 데이터셋과 평가셋도 버전을 나누어 관리했습니다.

**남긴 결정:** Hold는 단지 “조금 수상하다”의 다른 이름으로 쓰지 않습니다. 모델의 정보 부족 분류, 규칙에 의한 Safe→Hold 보정, 사용자의 응답에 따른 행동 보류를 각각 설명합니다.

## 4. 학습 결과를 실제 브라우저로 옮겼습니다

현재 C3 v2 epoch3는 KLUE RoBERTa-base 기반입니다. 학습 체크포인트를 ONNX로 변환하고 FP16으로 가중치를 저장하되 연산은 FP32로 유지합니다. 개발 입력 450개에서 학습 모델과 브라우저 실행물 사이의 판정 일치성을 확인한 뒤 운영에 연결했습니다.

**남긴 결정:** 모델과 토크나이저를 해시로 식별하고 실제 받은 모델 파일의 크기·해시를 검사합니다. 브라우저 실행 성공과 피싱 탐지 성능은 별도로 보고합니다.

## 5. 오판 가능성을 사용자 흐름에도 반영했습니다

최신 평가에서도 위험을 놓친 사례와 정상 문구에 대한 경고가 남았습니다. 이를 감추거나 모델의 Safe를 안전 인증으로 제시하지 않습니다.

**남긴 결정:** Safe 이후에도 민감한 행동 요구를 묻습니다. 이미 행동했다면 모델을 기다리지 않고 대응을 제공합니다. 기술 실패는 분석 불가로 표시하며, 너무 긴 입력을 잘라 안전하다고 판정하지 않습니다.

## 현재와 과거를 구분합니다

현재 출품 버전은 **2026년 9월 20일 배포한 C3 v2 epoch3와 해당 정책 조합**입니다. 과거 Gold 평가, 관찰 회귀, 개발 평가, 최신 고정 평가는 표본과 조건이 달라 하나의 성능 그래프로 비교하지 않습니다.

본 문서의 목적은 연구 분량을 강조하는 것이 아니라, 어떤 문제가 발견되었고 그에 따라 제품에서 무엇을 바꿨는지 설명하는 것입니다. 현재 결과와 한계는 [평가 문서](evaluation.md), 실제 동작은 [구조 문서](architecture.md)에서 확인할 수 있습니다.
